## 1. 다음 담당자가 먼저 알아야 할 결론

- 사용자 요청은 늦은 진입과 부정확한 알람 개선이다. 돌파·눌림 후보 포착과 목표 거리 계산을 결합한 수정안을 구현했고, 실제 보존 자료 비교 및 회귀 시험 455개를 완료했다.
- [PR #20](https://github.com/hekyun-ctrl/upbit-market-analyzer/pull/20)은 운영 브랜치에 병합됐다. **코드 병합과 실제 운영 배포는 다르다. 현재 LBank 실행 버전은 여전히 이전 커밋이다.**
- 사용자는 부정적 비교 결과를 전달받은 뒤 “운영에 적용해주세요”, “승인합니다”라고 명시했다. 적용 대상은 `capture` 모드다. 다만 Railway 연결 도구가 배포 승인 취소 응답을 반복해 새 배포는 생성되지 않았다.
- 이번 인수인계 작성에서는 배포를 재시도하지 않았다. 새 담당자는 최신 상태부터 확인해야 한다.
- **수익성·정확도 향상은 입증되지 않았다.** 제한된 실제 자료의 고정 청산 비교에서는 capture 추가 신호도 손절됐다. 이를 숨기거나 455개 시험 통과를 수익성 검증으로 표현하지 않는다.
- 가까운 지지·저항을 상위 방향 예외로 통과시키는 기존 정책은 이번 수정에 포함되지 않았다. “늦은 진입 문제가 모두 해결됐다”고 보고하면 안 된다.

## 4. 구현 내용과 유지한 제약

주요 파일:

- `lbank_entry_refinement.py`: `legacy` / `structure_cost` / `capture` 세 모드.
- `lbank_futures_monitor.py`: 모드 선택, 손절·목표 계산 연결, 후보와 최종 확인 연결, 실행 모드 기록.
- `lbank_structure_patterns.py`, `lbank_breakout_freshness.py`: 적응형 눌림 폭과 완료 1분봉 몸통 돌파 근거.
- `test_lbank_entry_refinement.py`: 추가 동작 시험 15개.
- `test_lbank_paper_notifications.py`: 의도적으로 바뀐 세 함수의 소스 해시만 갱신.

`structure_cost`는 돌파·눌림 손절 하한에 유효한 연속 완료 1분봉 ATR을 사용하고 비용 후 필요한 목표 거리를 다시 계산한다. 구조 고저점 밖의 손절은 유지한다. `capture`는 여기에 변동성에 따른 눌림 폭과 실제 완료 1분봉 돌파 포착을 추가한다. 탐지와 최종 확인은 같은 판정 근거를 사용한다. 박스 반등의 계산은 그대로다.

미설정 기본값은 `legacy`다. 위험·증거금 한도, 비용 후 손익비, 기존 알람 간격을 이번 변경에서 완화하지 않았다. **1시간·4시간 방향은 참고 기록이며 방향 불일치나 자료 부족을 추가 진입 차단 조건으로 만들지 않는다.** 자동 주문, 중지된 모의 알림·ZB 발송 재개는 승인된 변경 범위가 아니다.

## 6. 늦은 진입·정확도 문제에서 남은 핵심

10월 24일 19:07 KST까지 확인한 이전 운영 코드의 사례다. 10월 25일 실시간 성과로 표현하지 않는다.

- 10월 24일 00:17 돌파 숏 81,403.1 → 01:04:51 가격 81,682.0, 손절선 81,680.31 침범.
- 같은 날 09:36 눌림 숏 80,680.3 → 10:50:09 완료 5분봉 종가가 고정 구조를 넘어 무효화.
- 둘째 신호는 진입 바로 아래 지지 80,680.0 및 추가 지지들을 `single_pivots_under_aligned_15m_5m` 예외로 통과시켰다. 관찰가 80,680.1 대비 확인가 80,680.3이라 숏 방향 추가 진전도 거의 없었다.
- 두 신호의 후보→최종 확인은 약 31초, 발송 시작→Telegram 수락은 1초 미만이었다. Telegram 수락은 사용자 단말 수신 시각이 아니다. 긴 발송 대기보다 후보가 생기는 위치와 가까운 장벽 예외를 우선 검토할 근거다.
- 확인한 경고는 실제 가격·구조 이탈에 따른 것이다. 경고를 숨기거나 손절을 무작정 넓히는 것으로 정확도를 높였다고 하면 안 된다.
- 앞선 10월 22일에는 2차 목표 도달 사례도 있었다. 적은 사례로 일반 승률을 단정하지 않는다. 신호 번호가 배포 사이에 재사용됐으므로 번호만으로 결과를 결합하지 않는다.

추가 개선을 진행한다면 첫 미돌파 지지·저항까지 비용 후 공간, 실제 돌파/재시험 근거, 확인 뒤 방향 진전을 별도 변경으로 검토한다. 새 연속 자료에서 손절·목표 도달·기회 손실·알람 빈도를 함께 비교하고, 이 손실 사례에 맞춰 즉시 수치를 조정하지 않는다.

## 7. 6.1방에서 이어갈 순서

1. 운영·연구 브랜치 최신 SHA와 PR #20, Railway의 live/staged 소스 및 최신 배포를 확인한다. 새 변경이 있으면 위 표와 대조하고 충돌을 먼저 해결한다.
2. 이미 사용자가 직접 배포했다면 중복 배포하지 않는다. 새 배포 커밋이 의도한 수정안을 포함하는지 확인한다.
3. 아직 동일 대기 패치라면 승인 처리 상태를 확인한다. 이전 취소를 우회하거나 같은 실패를 반복 호출하지 않는다. 다른 사람이 추가한 대기 변경이 생겼다면 원래 1건이라고 가정해 환경 전체를 적용하지 않는다.
4. 배포가 진행되면 SUCCESS까지 확인한다. 빌드 생성·QUEUED·DEPLOYING만으로 완료라고 보고하지 않는다. 실패 시 해당 배포의 build/predeploy 로그만 먼저 확인한다.
5. 성공 후 다음 실제 로그와 상태를 확인한다.
   - `ENTRY_TIMING_RUNTIME commit=b4c7d94...` 또는 후속으로 검증한 커밋.
   - `ENTRY_REFINEMENT_POLICY mode=capture adaptive_capture=True continuation_local_stop=True profitability_validated=false`.
   - 완료 원본 봉의 연속성, 장부와 /data 저장 정상, 자료 준비 상태. 재시작 직후 미준비이면 준비 완료라고 쓰지 않는다.
   - 중지된 모의 알림과 ZB 발송이 계속 비활성인지 확인. 검증용 실제 메시지나 주문을 만들지 않는다.
6. PR #20 체크포인트에 실제 배포 ID·커밋·검증 결과를 갱신하고 사용자에게 한국어로 짧게 보고한다. 배포 확인만으로 수익성 검증 완료라고 표현하지 않는다.

회귀 시험과 과거 비교는 이미 완료했다. 새로운 코드 변경·실패·자료 불일치가 없으면 처음부터 반복하지 않는다. 추가 결함 수정은 최신 소스에서 별도 브랜치로 시작하며, 무관한 파일을 한꺼번에 커밋하지 않는다.
